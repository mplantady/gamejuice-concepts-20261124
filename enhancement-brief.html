01

One pipeline, twelve distinct games

The linked page is a catalog containing 12 originals, 12 conversions and 36 themed variants. The future goal covers all 12 games. Each needs its own reference contract; a shared visual recipe must never erase the distinctions that make its pieces, controls and outcomes understandable.

Keep

The recognizable game

Preserve demonstrated rules, input mapping, piece identity, board geometry, progression, HUD meaning and camera framing. Use the original as the behavioral baseline; use conversions and variants as supporting references.

Improve

Light, material, hierarchy

Give pieces cleaner shapes, controlled highlights and grounded depth. Refine UI spacing and typography within its existing footprint. Keep the strongest contrast on interactive pieces, goals and useful feedback.

Express

Polish tied to events

Use short, legible visual and sound responses at verified events. Camera movement is optional and restrained. Preserve the player’s view and target positions during every interaction.

Fidelity first for Royal Smash and Draft Showdown. Their source-reported conversion scores are below the catalog’s target of 92. Enhance the original’s demonstrated experience rather than inheriting unverified differences from those conversions.

Source: saved catalog · unaltered source HTML. The source describes converted projects as editable three.js builds. This archive is a reference collection, not a set of completed Unity projects.

Reported risk · Royal Smash

Appearance is not parity

The candy variant receives theme/polish 9/7, while the three variants report event timing 0.598–0.640 and real-tap reactions 0.374–0.597. The conversion reports CPU 791 → 979 ms/s and heap 34 → 46 MB.

Reported risk · Draft Showdown

Verify the active sequence

Variants report event timing 0.489–0.710 and real-tap reactions 0.440–0.713. The source’s Christmas review did not capture the result screen or CTA. Those states remain an evidence gap.

Evidence limits

Keep measurements honest

Timing compares sound starts within ±250 ms, not complete game logic. Reviewers saw contact sheets. CPU tests are noisy; Draft’s conversion CPU is 232 ms/s in one table and 126.7 in another. Do not combine those baselines.

03

The repeatable sequence

A / OBSERVEReference contractCapture real states and actions. Separate verified facts from missing evidence.
B / DESIGNImage conceptShow a higher-quality treatment of the same visible state and layout.
C / DIRECTVideo conceptExplore event-bound feedback, sound direction and restrained motion.
D / BUILD LATERUnity mockupTranslate the target into an editable scene using available Unity AI and CLI tools.

Reuse the prompt structure, not a fixed art style. Fill each contract from that game’s original build, screenshots and observed interaction. At every stage, compare against the original first. A failed fidelity check sends the artifact back for revision before it becomes input to the next stage.

For calibration, a high-scoring reference can establish the shared process; Royal Smash and Draft Showdown should then test whether the process handles harder fidelity problems. This sequencing does not remove either game from the 12-game scope.

04

Reusable prompt sequence

These are candidate templates, ready to fill and evaluate. Replace bracketed fields with observed evidence. Do not supply invented rules or imply that an attached screenshot proves behavior. Each step produces an explicit handoff to the next.

A. Build the gameplay and reference contract

Input: original playable, conversion, reference captures and a recorded interaction sequence. Output: a factual contract and any missing evidence.

Analyze [GAME_NAME] for a future Unity visual enhancement that stays close to the original gameplay.

Evidence supplied:
- Original playable: [LOCAL_ORIGINAL_PATH]
- Converted playable: [LOCAL_CONVERTED_PATH]
- Original screenshots with viewport and state labels: [CAPTURES]
- Recorded inputs and resulting states, with timestamps: [INTERACTION_RECORD]
- Source catalog notes: [SOURCE_NOTES]

Treat the original as the behavioral reference. Treat catalog scores and reviewer notes as source-reported clues, not independently verified facts. Inspect the provided evidence before describing rules. If a rule, transition, camera behavior or outcome is not demonstrated, mark it UNKNOWN and identify the capture needed to resolve it.

Produce a concise REFERENCE_CONTRACT containing:
1. Game identity, source paths, evidence IDs and capture dimensions.
2. The demonstrated objective, permitted inputs, valid/invalid action behavior, state transitions, progression, failure/retry and end states. Include only states that actually exist in the evidence.
3. A screen inventory: exact board/playfield geometry, visible piece counts and positions for each anchor state, identity-to-visual mapping, HUD values and copy, tutorial cues, overlays, interaction targets and safe areas.
4. Camera projection, framing and any demonstrated motion. Distinguish the rendering camera from the device viewport.
5. A verified event timeline: input → visible response → sound cue → resulting state. Record uncertainty instead of filling gaps.
6. IMMUTABLES: interaction rules, target geometry, piece identity, layout relationships, readable text and outcome conditions that the enhancement must preserve.
7. ALLOWED VISUAL CHANGES: material quality, controlled lighting, refined edges, UI craftsmanship and event-bound feedback that do not alter those immutables.
8. Baseline issues and separate enhancement opportunities. Label each as observed, source-reported, or proposed.
9. Comparison captures and replay checks required for this game.

Do not generate a new game or begin Unity implementation. Return the contract plus a short evidence-gap list. This contract will constrain the image, video and Unity stages.

B. Create the enhanced image concept

Input: a completed contract and exact original frame. Output: one reference-consistent visual target, plus a change list and fidelity review.

Create an enhanced visual concept for [GAME_NAME] using the attached original frame [ANCHOR_FRAME_ID] and REFERENCE_CONTRACT below.

[REFERENCE_CONTRACT]

Target: [OUTPUT_DIMENSIONS_AND_ASPECT_RATIO]. Art direction: [GAME_SPECIFIC_MATERIAL_AND_LIGHTING_DIRECTION]. Preserve the recognizable character of the original while making its lighting, graphics and UI feel more finished.

Treat the source frame as a precise composition and state reference. Preserve the same camera framing and projection; board/playfield outline; piece count, type, identity, position and orientation; active selection; HUD values; tutorial guidance; button positions; copy and state of play. Keep all pieces and controls within their original interaction footprints. Do not add or remove game objects, change a symbol's meaning, invent a new state, or introduce a new mechanic.

Improve craftsmanship within those constraints:
- Coherent materials, clean silhouettes and well-controlled highlights.
- Soft contact depth and lighting that support separation without hiding symbols or changing functional colors.
- Crisp icons and typography, consistent padding and refined surfaces within existing UI geometry.
- A quieter background and a clear hierarchy: playfield first, goals and feedback second, decoration last.
- An appearance that remains legible at actual phone size, including dimmed and selected states where relevant.

Avoid bloom over text, heavy depth of field, excessive gloss, particles over targets, large shadows across symbols, decorative objects that look interactive, or a perspective change. Preserve exact text; if the generator cannot reproduce it, mark that as unresolved and supply a separate exact UI overlay specification instead of approving altered copy.

Return the concept image, a concise list of intentional visual changes, and a fidelity checklist against the anchor frame. Flag any drift in geometry, count, identity, values or readability for revision. Label the result VISUAL CONCEPT — NOT A PLAYABLE BUILD.

C. Direct the video concept

Intended video stage: Seedance 2.5, subject to actual tool availability and supported inputs. This template makes no claim about access, duration limits, native audio or supported controls.

Create a short look-and-feel video concept for [GAME_NAME] from:
- The REFERENCE_CONTRACT: [CONTRACT]
- The selected enhanced image: [IMAGE_CONCEPT]
- The original reference sequence and matching anchor frames: [REFERENCE_VIDEO_OR_FRAMES]
- The verified event timeline: [EVENT_TIMELINE]
- Requested output: [ASPECT_RATIO, DURATION_AND_FRAMING]

Use Seedance 2.5 if it is available through the selected workflow, after checking its actual supported inputs and controls. Do not claim unsupported duration, audio, camera or reference-lock capabilities. If a requested feature is unavailable, identify that limit and retain its direction in a companion cue sheet rather than pretending it was rendered.

The visual concept defines materials, lighting and UI treatment. The original sequence defines gameplay and causality. Reproduce only demonstrated states and transitions in the same order. Preserve piece identity, board geometry, HUD meaning, tutorial cues, action targets and visible outcomes. Keep text stable. Do not hallucinate extra moves, rewards, clears, impacts, counters, menus, wins or physics behavior.

Add polish only at events confirmed by the timeline:
- Anticipation, contact highlights, short particles, trails or settling motion only where they clarify that specific event.
- Keep effects away from essential text and targets; make them decay before the next interaction.
- Use restrained ambient motion behind the playfield, with a stable, readable foreground.
- Preserve the demonstrated camera by default. Any optional emphasis must be very small, occur in a safe interval, and return to the exact reference frame before the next input. Never orbit, zoom or shake in a way that changes apparent target geometry or hides pieces. If that cannot be guaranteed, keep the camera fixed.
- Direct distinct, brief sound cues for the verified actions, with softer ambience and no masking of meaningful feedback. Retain the original event timing. Supply an audio cue sheet if synchronized audio is not supported; do not label silent or unverified audio as completed.

If only a static reference is available, animate lighting/ambient detail only. Do not invent gameplay to fill the clip. Request a real interaction sequence before showing a move or outcome.

Return the concept clip, an event-by-event VFX/audio/camera cue sheet, and a list of deviations or uncertain frames. Review start, event and end anchor frames against the contract. Label the video LOOK-AND-FEEL TARGET — NOT PROOF OF GAMEPLAY OR PHYSICS.

D. Hand off to a future Unity mockup

Input: the verified contract and selected art direction. Output: an editable Unity mockup and captured comparison, once implementation is requested.

Build an editable Unity mockup of [GAME_NAME] using the available, supported Unity AI and Unity CLI workflow in [UNITY_PROJECT]. Inspect the project and tool capabilities before choosing implementation steps. Follow its existing conventions.

Inputs:
- Original playable and source reference: [LOCAL_PATHS]
- Verified REFERENCE_CONTRACT and replay record: [CONTRACT_AND_REPLAY]
- Selected enhanced image concept: [IMAGE]
- Video look-and-feel target and event cue sheet: [VIDEO_AND_CUES]
- Target device/aspect ratios and performance budget: [TARGETS]

Authority order: demonstrated original gameplay and the contract determine behavior; the selected image determines visual direction; the video suggests effects and timing only where consistent with the original. Resolve contradictions against the original. Do not reproduce a video-generation error as gameplay.

Preserve input rules, interactive geometry, piece identity, state transitions, progression and outcomes. Keep rules separate from presentation so lighting, materials, UI, VFX, audio and optional camera emphasis can be tuned without changing behavior. For rules not yet established by evidence, stop that dependent portion and report the exact missing observation.

Create an editable scene with clearly named objects, reusable prefabs where useful, tunable materials, lighting, UI components and event-driven effects. Keep art references and source provenance available. Avoid baking the generated concept video into the scene as a substitute for working interactions. Keep camera movement disabled by default unless the reference contract permits it and target readability is preserved.

Implement the demonstrated interaction sequence. Hook visual and sound responses to real game events, not an unrelated decorative timeline. Make enhancements easy to toggle for baseline comparison. Preserve tutorial guidance and accurate HUD updates. Use the stated performance budget; do not infer mobile performance from source headless-browser numbers.

Capture the mockup at the same viewports and anchor states as the original. Replay the same inputs and compare outcomes, target positions, UI values, readability, transitions and sound timing. Include invalid-input, failure/retry and end-state checks only when those states exist in the original. Check both portrait and landscape/desktop where supported by the reference.

Return the editable scene and relevant assets, comparison captures, a completed shared quality rubric, measured performance on the stated test setup, and a concise list of remaining differences. State clearly which behaviors are implemented, which are mocked, and which remain unverified. Do not claim parity or completion based only on appearance.
05

One quality rubric for every game

Proposed scoring: 0 = fails or unverified; 1 = major gaps; 2 = meets the reference; 3 = clear improvement with fidelity preserved. Score only what a stage can demonstrate. Mark behavioral and performance rows “not yet testable” for image/video concepts; they cannot pass a Unity implementation gate.

DimensionEvidence to compareProposed acceptance rule
State and layout fidelityAnchor frames: piece counts, identity, positions, board geometry, framing, HUD values and exact UI text.At least 2. No missing or invented functional element.
Interaction and outcomesMatched inputs produce the demonstrated transitions and results; targets remain in the correct positions.At least 2 in the Unity mockup. Visual similarity cannot substitute.
Readability and guidancePhone-size review, functional color/symbol distinction, selected/disabled states, tutorial cues, text and effect overlap.At least 2. No loss of actionable information.
Lighting, materials and UICoherent surface treatment, controlled depth, clean silhouettes, accurate typography and visual hierarchy.Aim for 3. Improvement must remain clear with effects paused.
VFX, audio and cameraVerified event cue sheet, onset/decay, audibility, recovery before input, stable target geometry and state visibility.At least 2. Any unsafe camera effect is removed or disabled.
Responsive presentationMatching supported viewports: framing, safe areas, UI scale, overlays and end states.At least 2. No clipping or hidden interaction region.
Performance and editabilityMeasured target setup, stated frame/resource budget, editable scene objects and effects, clear behavior/presentation boundaries.At least 2 in Unity. Report actual measurements and remaining gaps.

Gate, not average: a strong art score cannot compensate for altered rules, missing guidance, broken input or unreadable targets. Resolve those failures first. The rubric and thresholds are proposed working criteria, not validated production standards.

06

What each future mockup carries forward

Per-game reference packet

  • Original and supporting conversion/variant paths.
  • Verified contract, labeled captures and interaction record.
  • Selected image with the exact-state fidelity review.
  • Video concept and explicit VFX/audio/camera cue sheet.
  • Editable Unity scene, comparison captures and completed rubric.
  • Known gaps, proposed improvements and measured results kept distinct.

Current boundary

This local brief is preparation for all 12 future mockups. The catalog analysis is source-based. The prompts still need to be exercised against actual per-game captures, then refined from the results.

No concept image, concept video or Unity implementation is claimed by this document. Before implementation, establish each game’s reference contract and select the visual direction that passes its fidelity checks.
